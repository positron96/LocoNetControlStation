The command station is based on ESP32 chip.
Development is done with Arduino core for ESP32 using PlatformIO framework and vscode IDE.

Feature list:

* [x] Running locos on main track via DCC
** [x] Constant refreshing of loco speed and first 12 functions
** [x] Priority-based DCC packet queue (more important packets are sent out first)
* [x] Ops mode programming on a dedicated DCC track (reading CVs works)
* [x] Fast clock
* Loconet interface
** Routing LocoNet messages to/from several sources:
*** [x] Physical LocoNet bus
*** [x] LbServer (LocoNet over TCP) over WiFi
*** [x] USB-Serial interface (present, but not used)
** [x] "Dispatch" of LocoNet slots
** [x] Fast clock (full clock master mode needs a code change, it's disabled now)
* [x] WiFi control via WiThrottle protocol (EngineDriver or WiThrottle)
* [x] OLED Display for information and diagnostic output
* [ ] Stored turnout roster (partially done)
* [ ] +++<del>DCC++ interface via USB-Serial or WiFi</del>+++ (No need at the moment)
* [ ] RailCom gap generation and reading (low priority)
* [ ] LCC interface (low priority)

The intended primary interface of the command station is LocoNet.
LocoNet messages are received and transmitted from physical LocoNet bus and WiFi.
However, LocoNet is not an essential part of the firmware and can be removed from project;
DCC packet generation with corresponding API can be used to implement other interfaces, like DCC++.

WiThrottle protocol is used to connect WiFi throttle to Command station and does not depend on LocoNet routing.

## Hardware

While the firmware can work on any ESP32 on a breadboard
  (provided pinout is followed or adjusted),
  main target for the project is a custom-designed PCB.

### v2 [WIP]

Second version of the hardware is being developed with these goals in mind:

* Fit the Command station into a DIN rail enclosure.
* Update DCC circuitry to modern ICs (instead of old L298N) to ease reading of current.
* Use official ESP32-DevKitC board instead of Lolin32 Lite to avoid problems with availability and quality.
* Modularize the design to allow adding new features without PCB redesign.
* Use USB-PD to power the board, use switching regulator instead of LM7805.
* Add a small OLED display for status and diagnostics.
* Limit current of LocoNet RailSync to better follow specs.

### v1

Version 1 PCB was designed in ~2021 with Lolin32 Lite ESP32 board
(due to it being one of the cheapest ESP32 board).
The board has L298N chip for DCC generation for both main and program tracks.

LocoNet part uses LM393 comparator with resistors adapted for 3.3V VCC levels.
This circuitry is common in DIY LocoNet projects{empty}footnote:[http://www.spcoast.com/pages/LocoShield.html]footnote:[https://images.beneluxspoor.net/bnls/LocoNet_Shield_Schema.png].

The PCB is open-source and is available here: https://oshwlab.com/positron96/loconet-command-station.

The project will also work on a breadboard with a L298N module (a red module is required as it exposes current sensing pins)
and DIP versions of components.
Other available LocoNet breakout boards will also work.
They must operate at 3.3V,
  5V levels on ESP32 GPIOs are out of spec (though it'll probably survive).

## Code architecture:

* link:lib/DCC[DCC library]: DCC packet generation and track output backend.
** Public include is `lib/DCC/include/DCC.h`; most internals live under `lib/DCC/include/dcc/` and `lib/DCC/src/`.
** `dcc::PacketList` (in `packet_list.hpp`) stores outgoing DCC packets and decouples packet preparation and scheduling from low-level transmission.
    Used internally by `BaseChannel`
** `dcc::BaseChannel` (in `base_channel.hpp`) is the abstract track interface (both main and program).
** `dcc::ESP32RMTChannel` (in `esp32_rmtcont_channel.hpp`) is the current ESP32 output implementation used by this project.
    This implementation has perfect timing, but maximum DCC packet size is limited by size of RMT blocks
    (ESP32 has plenty, but newer chips have much less).
** `dcc::ESP32RMTChannel` (in `esp32_channel.hpp`) is the previous ESP32 output implementation used by this project.
    It has some timing glitches every now and then.
** `dcc::ESP32TimerChannel` in `esp32_timer_channel.hpp` is the previous ESP32 output implementation, based on HW timer.
    Its timing accuracy was broken after update to newer ESP32 SDK.
** `dcc::PowerEvent` / `dcc::PowerObserver` (in `power_event.hpp`) are used for power and overcurrent notifications.

* link:lib/esp32-rmt-cont[ESP32 RMT continuous library]:
    An extract of legacy ESP32 RMT driver from ESP-IDF v5. Has its own link:lib/esp32-rmt-cont/README.md[README].

* `src/command_station.hpp/.cpp`: high-level command station API.
Handles locomotive slot allocation/ownership, speed/direction/functions,
  CV programming, turnout roster/state. Sends commands to DCC channel objects.

* `src/loconet_managers.hpp/.cpp`: LocoNet-related functionality.
** `LocoNetSlotManager` handles slot/programming/clock related LocoNet traffic.
** `LocoNetTurnoutManager` handles switch/accessory requests.

* `src/loconet_tcp_server.hpp`: `LbServer` implementation of http://loconetovertcp.sourceforge.net/Protocol/LoconetOverTcp.html[LocoNet over TCP].
It parses TCP frames, injects messages into LocoNet bus, and forwards bus traffic back to TCP clients.

* `src/loconet_serial.hpp`: LocoNet over UART transport.
Can be used for a serial PC-LocoNet link, but for now WiFi is used instead.

* `src/withrottle_server.hpp/.cpp`: server-side link:https://www.jmri.org/help/en/package/jmri/jmrit/withrottle/Protocol.shtml[WiThrottle protocol] implementation.
  Connects WiThrottle clients to command station data.

* `src/ui/`: UI components for OLED status display (`display.hpp/.cpp`, `status_screen.hpp`).

* `src/main.cpp`: contains wiring information and starts up the rest of the system.
    Initializes DCC channels, LocoNet bus/parsers/managers,
    WiFi services (LbServer/WiThrottle), timers, and display.
    Home to Arduino's `setup()` and `loop()` functions.

### LocoNet message routing

The project must accept Loconet messages from different sources:
  physical LocoNet bus, USB-Serial, LbServer (LocoNet over TCP).
All messages must be transparently routed to between all connected buses.

It means that:

 * There must be a routing mechanism for broadcasting messages from one source to others.
 * User components (e.g. Locomotive slot or Fast clock) must be separated from hardware backend and take messages from other sources.
 When command station itself generates a message (e.g. a reply to throttle),
   it must be broadcasted to all handlers.
 * Result of sending a message to the bus is only taken into account for real LocoNet bus;
   it is assumed that USB and WiFi always send packets successfully.

With this in mind, the LocoNet2 library was heavily redesigned and refactored.
The LocoNet class is now separated into hardware backend (LocoNetPhy),
  a message parser (LocoNetDispatcher), and a routing bus (LocoNetBus) between them.
Other sources of messages extend LocoNetConsumer class and are connected to the bus. and messages.
Frontend classes (Throttle, FastClock, SystemVariable etc) are connected to the message parser instead of hardware class and so can handle messages from all sources.

The project implementation is based on these libraries:

 *  https://github.com/positron96/LocoNet2[LocoNet2] (https://github.com/mrrwa/LocoNet2[upstream original]) - LocoNet bus support.
   The library is heavily modified to support several sources of loconet messages and to better use timers and RTOS tasks.
   (most of the changes were merged into upstream original, but there differences anyway).

 * Historically, link:lib/DCC[DCC] library was based on https://github.com/positron96/DCCpp[DCCpp library] and https://github.com/DccPlusPlus/BaseStation[DCC++ project].
   Since then it was gradually changed and shares no code, architecture or implementation with those projects.

 * https://github.com/positron96/withrottle[WifiThrottle] ESP8266 WiThrottle to DCC++ bridge.
   Mostly rewritten from scratch with the help of https://www.jmri.org/[JMRI] documentation and sources.

 * https://www.etlcpp.com/[Embedded Template Library] for statically-sized maps, vectors, bitsets etc.


## Journal

### 2023-02

**Beware that CV reading/writing may not work for your decoder.**

It appears that ADC on my esp32 changed its parameters over the year.
It now does not detect decoder responses when reading/writing CVs.
I tested with one particular decoder, the voltage over the shunt resistor is around 30mV, the resistor is 0.1 Ohm, so the current is 0.3A, which is within NMRA specs for basic acknowledge.
However, the ESP32 shows non-zero readings only starting from around 80 mV, and ADC readings are around 2-8.
This is actually within specs of ESP32 that https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32/api-reference/peripherals/adc.html#adc-attenuation[state] that measurable readings start from 100 mV.
Somehow it did work much better before, as I have the ADC threshold in the code at 500 before.
I had to lower it to 2, so now the CV reading somewhat works, but not reliably.

In the future version, a proper amplifier needs to be adde to the schematic.
I am looking at this TI https://www.ti.com/product/INA180[INA180].

### 2026-06

I've returned to work on this project after a long break.
The main goal is to remake the PCB for a DIN rail enclosure,
  but I started with adding support for periodic refreshing locomotive functions
  (they were one shot before) and upgrading the codebase to
  use modern  versions of SDK and libraries and C++ standard.
Last version before redesign is marked 1.0.

Upgrading code for ESP-IDF v5 caused the timer to break,
  as the jitter is too large with the new API for some reason.
I was able to somewhat combat this by switching to RMT peripheral,
  but it's also suffering from problems due to delays between RMT transmissions.
In new SDK RMT peripheral has completely new API which link:https://github.com/espressif/esp-idf/issues/13003[doesn't allow continous streaming].
So, while the new version mostly works (and has some important fixes to existing functionality),
  it needs a reimplementation of DCC.
The options I'm considering is back-porting of older RMT driver
  or trying an built-in ULP co-processor.
